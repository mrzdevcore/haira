\chapter{Error Handling}
\label{ch:errors}

\haira{} uses explicit error handling inspired by Go. Errors are values, not exceptions. Functions that can fail return both a result and an optional error.

For concise code, \haira{} also provides a \code{?} propagation operator and \keyword{try}/\keyword{catch} blocks built on Go's \code{panic}/\code{recover} mechanism.

\section{Philosophy}

\begin{itemize}
    \item \textbf{Errors are values} -- Not special control flow
    \item \textbf{Explicit handling} -- Callers must handle or propagate errors
    \item \textbf{Two modes} -- Verbose-but-clear tuple checking, or concise \code{?} propagation
    \item \textbf{Composable} -- Errors can be wrapped and chained
\end{itemize}

\section{The Error Type}

The built-in \type{Error} type represents errors:

\begin{lstlisting}
struct Error {
    message: string
    code: int?
    source: Error?
}
\end{lstlisting}

\subsection{Creating Errors}

\begin{lstlisting}
// Simple error
err = Error{message: "something went wrong"}

// With error code
err = Error{message: "permission denied", code: 403}

// Wrapped error (error chaining)
err = Error{
    message: "failed to read config",
    source: original_error
}
\end{lstlisting}

\section{Error Return Pattern}

Functions that can fail return a tuple of \code{(result, Error?)}:

\begin{lstlisting}
fn divide(a: int, b: int) -> (int, Error?) {
    if b == 0 {
        return 0, Error{message: "division by zero"}
    }
    return a / b, nil
}

fn read_file(path: string) -> (string, Error?) {
    // Implementation
}

fn parse_int(s: string) -> (int, Error?) {
    // Implementation
}
\end{lstlisting}

\section{Handling Errors}

\subsection{Basic Error Checking}

The standard pattern: call a function, check the error, handle or return:

\begin{lstlisting}
result, err = divide(10, 0)
if err != nil {
    io.println("Error: " + err.message)
    return
}
io.println("Result: " + to_string(result))
\end{lstlisting}

\subsection{Propagating Errors}

\begin{lstlisting}
fn process_file(path: string) -> (Data, Error?) {
    content, err = read_file(path)
    if err != nil {
        return Data{}, err  // Propagate error
    }

    data, err = parse_data(content)
    if err != nil {
        return Data{}, err  // Propagate error
    }

    return data, nil
}
\end{lstlisting}

\subsection{Wrapping Errors}

Add context when propagating:

\begin{lstlisting}
fn load_config(path: string) -> (Config, Error?) {
    content, err = read_file(path)
    if err != nil {
        return Config{}, Error{
            message: "failed to load config from " + path,
            source: err
        }
    }

    config, err = parse_config(content)
    if err != nil {
        return Config{}, Error{
            message: "invalid config format",
            source: err
        }
    }

    return config, nil
}
\end{lstlisting}

\section{Error Propagation Operator (\code{?})}

The \code{?} operator is syntactic sugar for ``panic on error.'' It extracts the success value from a call that returns \code{(T, Error?)}. If the error is non-nil, it panics.

\begin{lstlisting}
// These two are equivalent:

// Verbose
content, err = read_file(path)
if err != nil {
    panic(err)
}

// Concise
content = read_file(path)?
\end{lstlisting}

The \code{?} operator makes code much shorter when chaining multiple fallible calls:

\begin{lstlisting}
fn setup() {
    config = load_config("app.toml")?
    db = connect_database(config.db_url)?
    cache = init_cache(config.cache_url)?
    // If any call fails, execution stops with a panic
}
\end{lstlisting}

\begin{warning}
The \code{?} operator panics on error. If used outside a \keyword{try} block, an unhandled error will crash the program. Use \code{?} inside \keyword{try}/\keyword{catch} blocks, or in initialization code where failure is fatal.
\end{warning}

\section{Try/Catch}

The \keyword{try}/\keyword{catch} block recovers from panics caused by the \code{?} operator (or explicit \code{panic()} calls). It compiles to Go's \code{defer}/\code{recover} pattern.

\begin{lstlisting}
try {
    config = load_config("app.toml")?
    db = connect_database(config.db_url)?
    start_server(db)
} catch err {
    io.println("Startup failed: " + err)
    os.exit(1)
}
\end{lstlisting}

The catch variable receives the error as a string. Variables assigned inside the \keyword{try} block are hoisted and remain accessible after the block.

\subsection{Try/Catch in Functions}

\begin{lstlisting}
fn process_batch(items: [string]) -> int {
    count = 0
    for item in items {
        try {
            result = parse_item(item)?
            save_result(result)?
            count = count + 1
        } catch err {
            io.eprintln("Skipping item: " + err)
        }
    }
    return count
}
\end{lstlisting}

\section{Orelse Operator}

The \keyword{orelse} operator provides a default value when a fallible call fails:

\begin{lstlisting}
// If parse fails, use 0 as default
count = parse_int(input) orelse 0

// If config load fails, use defaults
config = load_config("app.toml") orelse Config{port: 8080}
\end{lstlisting}

This is useful for optional operations where a sensible default exists.

\section{Defer and Errdefer}

\subsection{Defer}

Use \keyword{defer} to ensure cleanup happens when the enclosing scope exits, regardless of how it exits:

\begin{lstlisting}
fn with_file(path: string) -> (string, Error?) {
    file, err = fs.open(path)
    if err != nil {
        return "", err
    }
    defer fs.close(file)  // Always closes, even on error

    content, err = fs.read_all(file)
    if err != nil {
        return "", err  // file is closed by defer
    }

    return content, nil  // file is closed by defer
}
\end{lstlisting}

\subsection{Errdefer}

The \keyword{errdefer} statement runs cleanup only when the enclosing scope exits via a panic (from \code{?} or explicit \code{panic}). If the scope exits normally, the errdefer does not run.

\begin{lstlisting}
fn setup_resources() {
    db = connect_database()?
    errdefer db.close()  // Only closes if a later ? panics

    cache = connect_cache()?
    errdefer cache.close()  // Only closes if a later ? panics

    // If migrate fails, both db and cache are closed
    migrate(db)?
    start_server(db, cache)
    // If we get here, errdefers do NOT run -- resources stay open
}
\end{lstlisting}

\section{Error Checking Patterns}

\subsection{Guard Pattern}

Check errors early and return:

\begin{lstlisting}
fn process(input: string) -> (Output, Error?) {
    // Guard: validate input
    if string.len(input) == 0 {
        return Output{}, Error{message: "input cannot be empty"}
    }

    // Guard: check prerequisites
    ready, err = check_ready()
    if err != nil {
        return Output{}, err
    }
    if not ready {
        return Output{}, Error{message: "system not ready"}
    }

    // Main logic
    result = do_processing(input)
    return result, nil
}
\end{lstlisting}

\section{Error Utilities}

\subsection{Checking Error Types}

\begin{lstlisting}
fn is_not_found(err: Error?) -> bool {
    if err == nil {
        return false
    }
    return err.code == 404 or string.contains(err.message, "not found")
}
\end{lstlisting}

\subsection{Error Chain Traversal}

\begin{lstlisting}
fn root_cause(err: Error?) -> Error? {
    if err == nil {
        return nil
    }
    current = err
    while current.source != nil {
        current = current.source
    }
    return current
}
\end{lstlisting}

\section{Option Types and Errors}

For operations that may not find a value (not an error condition), use option types:

\begin{lstlisting}
// Use option when "not found" is normal
fn find_user(id: int) -> User? {
    // Returns nil if not found
}

// Use error when "not found" is exceptional
fn get_user(id: int) -> (User, Error?) {
    // Returns error if not found
}
\end{lstlisting}

\section{Panic}

For truly unrecoverable situations, use \code{panic}:

\begin{lstlisting}
fn assert(condition: bool, message: string) {
    if not condition {
        panic(message)
    }
}
\end{lstlisting}

\begin{warning}
\code{panic} crashes the program unless caught by \keyword{try}/\keyword{catch}. Use it only for programming errors and invariant violations. Prefer returning errors for all expected failure conditions.
\end{warning}

\section{Best Practices}

\begin{itemize}
    \item \textbf{Return errors, don't log and continue} -- Propagate failures to the caller
    \item \textbf{Add context when wrapping} -- Use \code{Error\{message: "context", source: err\}}
    \item \textbf{Handle at the right level} -- Low-level returns specific errors, high-level decides what to do
    \item \textbf{Use \code{?} for chain-or-fail sequences} -- Cleaner than repeated \code{if err != nil}
    \item \textbf{Use \keyword{orelse} for optional operations} -- When a default is acceptable
    \item \textbf{Use \keyword{errdefer} for resource cleanup} -- Pairs allocation with deallocation
\end{itemize}

\section{Error Handling Grammar}

\begin{lstlisting}[language=EBNF]
error_return    = "(" type "," "Error?" ")" ;

error_check     = "if" identifier "!=" "nil" block ;

error_create    = "Error" "{"
                  "message" ":" expression
                  [ "," "code" ":" expression ]
                  [ "," "source" ":" expression ]
                  "}" ;

propagate_expr  = expression "?" ;

orelse_expr     = expression "orelse" expression ;

try_stmt        = "try" block "catch" identifier block ;

defer_stmt      = "defer" expression ;

errdefer_stmt   = "errdefer" expression ;
\end{lstlisting}
