\chapter{Workflows}
\label{ch:workflows}

Workflows are the central abstraction in \haira{}. A workflow is a composable function with a trigger, typed parameters, and a typed return value. Workflows replace both n8n-style visual automations and LangGraph-style agent graphs.

\section{Workflow Declaration}

A workflow is a function preceded by a trigger decorator:

\begin{lstlisting}
@trigger_type("config")
workflow WorkflowName(param: Type, param: Type) -> ReturnType {
    // body
}
\end{lstlisting}

Workflows without a trigger decorator can be called as sub-workflows but cannot be triggered externally.

\section{Triggers}

Triggers define how a workflow is invoked. They use the \code{@} decorator syntax.

\subsection{@webhook --- HTTP Endpoint}

\begin{lstlisting}
@webhook("/summarize")
workflow Summarizer(url: string) -> Summary {
    content = fetch_page(url)
    summary = Researcher.ask("Summarize: {content}")
    return Summary{ text: summary, word_count: summary.len() }
}
\end{lstlisting}

The workflow parameters become the JSON request body. The return type becomes the JSON response body.

\begin{lstlisting}[language=bash,numbers=none]
$ curl -X POST http://localhost:8080/summarize \
    -d '{"url": "https://example.com/article"}'

{"text": "...", "word_count": 150}
\end{lstlisting}

Options:

\begin{lstlisting}
@webhook("/path")                  // POST (default)
@webhook("/path", method: "GET")   // GET
@webhook("/path", method: "PUT")   // PUT
\end{lstlisting}

\subsection{@websocket --- Bidirectional Streaming}

\begin{lstlisting}
@websocket("/chat")
workflow Chat(message: string, session_id: string) -> stream<string> {
    return Assistant.stream(message, session: session_id)
}
\end{lstlisting}

WebSocket workflows receive messages and can return \code{stream<string>} for real-time streaming responses.

\subsection{@cron --- Scheduled Execution}

\begin{lstlisting}
@cron("0 9 * * *")  // every day at 9 AM
workflow DailyReport() -> Report {
    data = fetch_metrics()
    report: Report, _ = Analyst.run(AnalyzeRequest{ data: data })
    send_email("team@company.com", "Daily Report", report.summary)
    return report
}
\end{lstlisting}

Cron expressions follow standard cron syntax (minute, hour, day-of-month, month, day-of-week).

\subsection{@event --- Event-Driven}

\begin{lstlisting}
@event("order.created")
workflow ProcessOrder(order: Order) -> OrderResult {
    validated = validate_order(order)
    if validated.has_errors {
        return OrderResult{ status: "rejected" }
    }
    charge_payment(order)
    return OrderResult{ status: "confirmed" }
}
\end{lstlisting}

Events are published using \code{haira.emit()}:

\begin{lstlisting}
haira.emit("order.created", Order{ id: "123", total: 99.99 })
\end{lstlisting}

\subsection{@manual --- CLI Only}

\begin{lstlisting}
@manual
workflow Migrate(version: string) -> { status: string } {
    // only invoked from CLI or main()
    run_migrations(version)
    return { status: "done" }
}
\end{lstlisting}

\begin{lstlisting}[language=bash,numbers=none]
$ haira run Migrate --input '{"version": "v2"}'
\end{lstlisting}

\subsection{No Trigger (Sub-Workflow)}

Workflows without a trigger can only be called from other workflows or from \code{main()}:

\begin{lstlisting}
workflow EnrichLead(email: string) -> EnrichedLead {
    company = lookup_company(email)
    social = lookup_social(email)
    return EnrichedLead{ email: email, company: company, social: social }
}
\end{lstlisting}

\section{Sequential Steps}

The workflow body is sequential by default. Each line can use the results of previous lines:

\begin{lstlisting}
@manual
workflow ArticlePipeline(topic: string) -> Article {
    // Step 1: Research
    research: ResearchResult, err = Researcher.run(ResearchRequest{ topic: topic })
    if err != nil { return Article{}, err }

    // Step 2: Write draft
    draft: Article, err = Writer.run(WriteRequest{
        content: research.summary,
        sources: research.sources
    })
    if err != nil { return Article{}, err }

    return draft
}
\end{lstlisting}

\section{Named Steps}
\label{sec:named-steps}

The \keyword{step} keyword creates named, observable regions within a workflow body. Each step has a string label and a block of statements. The runtime automatically emits structured telemetry for every step---start time, end time, duration, and success/failure status---giving production-grade observability with zero manual logging.

\subsection{Syntax}

\begin{lstlisting}
step "Step Name" {
    // statements
}
\end{lstlisting}

A \keyword{step} is only valid inside a \keyword{workflow} body (including inside \keyword{spawn} blocks within workflows). The step name must be a string literal.

\subsection{Transparent Scope}

Steps are \emph{not} functions---they are labeled regions of the enclosing workflow. Variables assigned inside a step are visible to all subsequent steps and to the rest of the workflow body. A \keyword{return} inside a step returns from the enclosing workflow.

\begin{lstlisting}
@webhook("/api/process")
workflow ProcessData(input: string) -> { status: string, count: int } {
    step "Parse input" {
        records = parse_csv(input)?
        count = len(records)
    }

    step "Validate" {
        // `records` and `count` are visible here
        errors = validate_records(records)
        if len(errors) > 0 {
            // returns from ProcessData, not just the step
            return { status: "invalid", count: 0 }
        }
    }

    step "Save to database" {
        save_all(records)?
    }

    return { status: "ok", count: count }
}
\end{lstlisting}

This matches the n8n/Zapier mental model: every node's output flows to downstream nodes.

\subsection{Automatic Telemetry}

The runtime emits structured log events for each step without any explicit logging code:

\begin{lstlisting}[language=bash,numbers=none]
[ProcessData] step:start  "Parse input"
[ProcessData] step:end    "Parse input"        duration=42ms   status=success
[ProcessData] step:start  "Validate"
[ProcessData] step:end    "Validate"           duration=3ms    status=success
[ProcessData] step:start  "Save to database"
[ProcessData] step:end    "Save to database"   duration=156ms  status=success
\end{lstlisting}

If a step fails (via error propagation or early return), the telemetry reflects it:

\begin{lstlisting}[language=bash,numbers=none]
[ProcessData] step:start  "Validate"
[ProcessData] step:end    "Validate"           duration=3ms    status=failed   error="Validation failed"
\end{lstlisting}

This gives operations teams per-step visibility in production:
\begin{itemize}
    \item Which step is slow (duration)
    \item Which step failed (status + error message)
    \item Dashboards and alerts per workflow per step
\end{itemize}

\subsection{Parallel Steps}

Use existing \keyword{spawn} blocks to run steps concurrently---no new syntax needed:

\begin{lstlisting}
workflow ProcessOrder(order: Order) -> Result {
    step "Validate order" {
        validate(order)?
    }

    // These run in parallel
    spawn {
        step "Check inventory" {
            stock = check_stock(order.items)
        }
        step "Verify payment" {
            payment = verify_payment(order.card)
        }
    }

    // Back to sequential --- stock, payment available after spawn completes
    step "Fulfill" {
        fulfill(order, stock, payment)
    }

    return Result{ status: "fulfilled" }
}
\end{lstlisting}

Telemetry shows overlapping timestamps for parallel steps:

\begin{lstlisting}[language=bash,numbers=none]
[ProcessOrder] step:start  "Check inventory"
[ProcessOrder] step:start  "Verify payment"
[ProcessOrder] step:end    "Check inventory"    duration=120ms  status=success
[ProcessOrder] step:end    "Verify payment"     duration=200ms  status=success
\end{lstlisting}

Variables from parallel steps flow to workflow scope after the \keyword{spawn} block completes (spawn is a synchronization point).

\subsection{Real-World Example}

A data pipeline with multiple stages, each automatically traced:

\begin{lstlisting}
@webhook("/api/upload-config")
workflow UploadConfig(file_path: string) -> { status: string, message: string } {
    filename = file_path | string.split("/") | last()

    step "Open Excel" {
        wb = excel.open(file_path)?
        defer wb.close()
        index_rows = wb.read_sheet("index")?
    }

    step "Extract table data" {
        table_data = {}
        for row in index_rows {
            sheet = wb.read_sheet(row["sheet_name"])?
            table_data[row["table_name"]] = sheet
        }
    }

    step "Validate" {
        validation = validate_data(table_data)
        if !validation.is_valid {
            return { status: "error", message: "Validation failed: ${validation.errors}" }
        }
    }

    step "Push to GitLab" {
        branch = "feature/${filename}"
        create_branch(branch)?
        for name, data in table_data {
            sql = generate_sql(name, data)
            commit_file(branch, "${name}.sql", sql)?
        }
        create_merge_request(branch, "Update ${filename}")?
    }

    step "Wait for CI/CD" {
        poll_pipeline(branch)?
    }

    return { status: "success", message: "Deployed ${filename}" }
}
\end{lstlisting}

Without \keyword{step}, this workflow would need 10+ manual \code{io.println} calls to achieve the same observability. With \keyword{step}, every stage is automatically traced in production.

\section{Parallel Execution}

Use \keyword{spawn} blocks to run steps in parallel:

\begin{lstlisting}
@manual
workflow ReviewArticle(article: Article) -> [Review] {
    reviews = spawn {
        Reviewer.run(ReviewRequest{ article: article, focus: "accuracy" })
        Reviewer.run(ReviewRequest{ article: article, focus: "clarity" })
        Reviewer.run(ReviewRequest{ article: article, focus: "engagement" })
    }
    return reviews
}
\end{lstlisting}

A \keyword{spawn} block runs all statements concurrently and returns a list of results when all complete. This is equivalent to \code{Promise.all()} in JavaScript.

\section{Branching}

Standard \keyword{if}/\keyword{else} and \keyword{match} work inside workflows:

\begin{lstlisting}
@event("order.created")
workflow ProcessOrder(order: Order) -> OrderResult {
    validated = validate_order(order)

    if validated.has_errors {
        send_slack("#alerts", "Order {order.id} failed")
        return OrderResult{ status: "rejected" }
    }

    stock = check_stock(validated.items)

    if stock.available {
        charge_payment(order)
        send_email(order.customer_email, "Order confirmed!")
        return OrderResult{ status: "confirmed" }
    } else {
        send_email(order.customer_email, "Items out of stock")
        return OrderResult{ status: "backordered" }
    }
}
\end{lstlisting}

\section{Loops}

\begin{lstlisting}
@manual
workflow ProcessBatch(urls: [string]) -> [string] {
    results = for url in urls {
        content = fetch_page(url)
        Researcher.ask("Summarize: {content}")
    }
    return results
}
\end{lstlisting}

Loops inside workflows are sequential by default. For parallel iteration, use \keyword{spawn}:

\begin{lstlisting}
@manual
workflow ProcessBatchParallel(urls: [string]) -> [string] {
    results = spawn {
        for url in urls {
            fetch_page(url) | Researcher.ask("Summarize: {_}")
        }
    }
    return results
}
\end{lstlisting}

\section{Sub-Workflows}

Workflows can call other workflows like functions:

\begin{lstlisting}
workflow ScoreLead(company: Company, social: SocialProfile) -> ScoreResult {
    score: ScoreResult, err = Analyst.run(ScoreRequest{
        company: company,
        social: social
    })
    return score
}

workflow EnrichLead(email: string) -> EnrichedLead {
    company = lookup_company(email)
    social = lookup_social(email)
    score = ScoreLead(company, social)
    return EnrichedLead{ email: email, company: company, score: score.value }
}

@webhook("/new-lead")
workflow SalesAutomation(email: string) -> { result: string } {
    lead = EnrichLead(email)

    if lead.score > 0.8 {
        send_slack("#sales", "Hot lead: {email}")
    }

    return { result: "processed" }
}
\end{lstlisting}

Sub-workflows compose naturally. The compiler validates type compatibility at each call site.

\section{Error Handling}

Workflows use standard \haira{} error handling:

\begin{lstlisting}
@manual
workflow SafeProcess(data: string) -> { result: string } {
    result, err = risky_operation(data)
    if err != nil {
        send_slack("#errors", "Failed: {err.message}")
        result = fallback_operation(data)
    }
    return { result: result }
}
\end{lstlisting}

\section{Orchestration Patterns}

\haira{} workflows compose naturally into common orchestration patterns using existing language primitives. No special keywords or frameworks are needed.

\subsection{Sequential Chain}

Pipe the output of one agent into the next:

\begin{lstlisting}
workflow Analyze(text: string) -> { result: string } {
    summary, err = Summarizer.ask(text)
    sentiment, err = SentimentAnalyzer.ask(summary)
    report, err = ReportWriter.ask(sentiment)
    return { result: report }
}
\end{lstlisting}

\subsection{Parallel Fan-Out}

Run multiple agents concurrently and collect results:

\begin{lstlisting}
workflow Research(topic: string) -> { synthesis: string } {
    results = spawn {
        WebSearcher.ask(topic)
        PaperAnalyzer.ask(topic)
        NewsScanner.ask(topic)
    }
    synthesis, err = Synthesizer.ask(results)
    return { synthesis: synthesis }
}
\end{lstlisting}

\subsection{Router / Dispatcher}

One agent classifies intent, then \keyword{match} routes to a specialist:

\begin{lstlisting}
workflow Support(message: string, session_id: string) -> { reply: string } {
    intent, err = Router.ask(message)
    reply, err = match intent {
        "billing"   => BillingAgent.ask(message, session: session_id)
        "technical" => TechAgent.ask(message, session: session_id)
        _           => GeneralAgent.ask(message, session: session_id)
    }
    return { reply: reply }
}
\end{lstlisting}

\subsection{Handoff}

Agents delegate to other agents automatically via the \code{handoffs} field. See Chapter~\ref{ch:agents}, Handoffs section.

\subsection{Iterative Refinement}

An agent produces output, a critic evaluates it, and the loop repeats until approved:

\begin{lstlisting}
workflow Refine(draft: string) -> { result: string } {
    current = draft
    for i in 0..3 {
        critique, err = Critic.ask(current)
        if critique == "approved" { break }
        current, err = Writer.ask("Improve based on: ${critique}\n\n${current}")
    }
    return { result: current }
}
\end{lstlisting}

\subsection{Supervisor}

A planner creates a task list, workers execute each step, and a supervisor evaluates results:

\begin{lstlisting}
workflow ComplexTask(goal: string) -> { result: string } {
    plan, err = Planner.ask(goal)

    for step in plan.steps {
        worker = match step.type {
            "code"     => Coder
            "research" => Researcher
            "review"   => Reviewer
        }
        result, err = worker.ask(step.instruction)

        evaluation, err = Supervisor.ask("Evaluate: ${result}")
        if evaluation == "retry" {
            result, err = worker.ask("Try again: ${step.instruction}")
        }
    }

    return { result: result }
}
\end{lstlisting}

\subsection{Voting / Consensus}

Multiple agents answer the same question, then an aggregator picks the best:

\begin{lstlisting}
workflow Decide(question: string) -> { answer: string } {
    votes = spawn {
        ExpertA.ask(question)
        ExpertB.ask(question)
        ExpertC.ask(question)
    }
    consensus, err = Aggregator.ask(votes)
    return { answer: consensus }
}
\end{lstlisting}

\subsection{Human-in-the-Loop}

For workflows that require human approval, split into two workflows connected by shared state. The first workflow does the AI work and sends a notification. The second workflow handles the human's response:

\begin{lstlisting}
tool send_email(to: string, subject: string, body: string) -> string {
    """Send an email notification."""
    resp, err = http.post("https://api.sendgrid.com/v3/mail/send", {
        to: to, subject: subject, body: body
    })
    return resp.body
}

@webhook("/api/publish")
workflow SubmitForReview(content: string) -> { review_id: string } {
    edited, err = Editor.ask(content)
    review_id = save_review(edited)

    send_email(
        to: "admin@company.com",
        subject: "Review needed",
        body: "Approve: https://app.com/api/review?id=${review_id}&action=approve"
    )

    return { review_id: review_id }
}

@webhook("/api/review")
workflow HandleReview(id: string, action: string) -> { status: string } {
    if action == "approve" {
        content = get_review(id)
        publish(content)
        return { status: "published" }
    }
    return { status: "rejected" }
}
\end{lstlisting}

No new primitives are needed. The ``event'' is just another HTTP request hitting another workflow. Notifications go out via tools (email, Slack, etc.), and the callback URL points back to a \code{@webhook} workflow.

\section{Verification Loops}

The \keyword{verify} block groups assertions inside a workflow step. When combined with \code{@retry}, failed assertions automatically trigger a retry of the step.

\begin{lstlisting}
@webhook("/api/generate")
workflow GenerateCode(spec: string) -> { code: string } {
    @retry(3)
    step "Generate and validate" {
        code, err = Coder.ask(spec)
        if err != nil { return { code: "" } }

        verify {
            assert code.contains("fn main"), "must have main function"
            assert !code.contains("unsafe"), "no unsafe code allowed"
        }
    }

    return { code: code }
}
\end{lstlisting}

When a \keyword{verify} assertion fails inside a \code{@retry} step, the step is retried up to the specified number of times. If all retries fail, the workflow continues with the last result.

\begin{note}
\keyword{verify} is only meaningful inside steps decorated with \code{@retry}. Without \code{@retry}, a failed assertion simply panics (as with standalone \keyword{assert}).
\end{note}

\section{Lifecycle Hooks}

Steps and workflows support lifecycle hooks for error handling, success callbacks, and cancellation:

\begin{lstlisting}
@webhook("/api/process")
workflow ProcessData(input: string) -> { status: string } {
    step "Process" {
        result = heavy_computation(input)?
    }

    onerror(err) {
        send_slack("#alerts", "Process failed: ${err}")
    }

    onsuccess {
        send_slack("#ops", "Process completed successfully")
    }

    return { status: "ok" }
}
\end{lstlisting}

\section{Eval Framework}

The \keyword{eval} declaration defines automated agent evaluations with test cases and scoring thresholds:

\begin{lstlisting}
eval "classifier accuracy" {
    agent: Classifier
    cases: [
        { input: "I love this!", expected: "positive" },
        { input: "This is terrible", expected: "negative" },
        { input: "It's okay I guess", expected: "neutral" }
    ]
    threshold: 0.8
}
\end{lstlisting}

Run evaluations with the CLI:

\begin{lstlisting}[language=bash,numbers=none]
$ haira eval main.haira

Running eval: classifier accuracy
  [PASS] Case 1: I love this!
  [PASS] Case 2: This is terrible
  [FAIL] Case 3: It's okay I guess
         Expected: neutral
         Got:      positive

Score: 66.7% (2/3 passed)
Result: FAIL (threshold: 80%, got: 67%)
\end{lstlisting}

\section{Cross-Harness Export}

\haira{} programs can be exported as Claude Code agent configurations:

\begin{lstlisting}[language=bash,numbers=none]
$ haira build main.haira --target claude-code
\end{lstlisting}

This generates:

\begin{lstlisting}[language={},numbers=none]
.claude/
  agents/agent-name.md      # Agent system prompt + config
  commands/workflow-name.md  # Slash commands for workflows
  mcp-servers.json           # Points to MCP binary
bin/
  haira-tools                # MCP server with custom tools
\end{lstlisting}

Each agent becomes a Claude Code agent markdown file. Custom tools are compiled into an MCP server binary that Claude Code connects to via \code{mcp-servers.json}.

\section{Workflow Grammar}

\begin{lstlisting}[language=EBNF]
workflow_decl = { decorator } "workflow" identifier
                "(" [ params ] ")" [ "->" type ] block
                { lifecycle_hook } ;

decorator     = "@" identifier [ "(" [ arguments ] ")" ] ;

spawn_block   = "spawn" "{" { statement } "}" ;

step_stmt     = "step" string_literal { decorator } block
                { lifecycle_hook } ;

verify_stmt   = "verify" block ;

eval_decl     = "eval" string_literal "{" { eval_field } "}" ;

eval_field    = identifier ":" expression ;

lifecycle_hook = "onerror" "(" identifier ")" block
               | "onsuccess" [ "(" identifier ")" ] block
               | "oncancel" block ;
\end{lstlisting}
